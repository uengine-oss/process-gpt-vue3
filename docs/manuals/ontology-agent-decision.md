# 온톨로지 근거 에이전트 판단 — 유형별 테스트 진행 문서

프로세스를 실행하다 보면 에이전트가 사람 대신 무언가를 골라야 하는 단계가 있습니다. 예를 들어 견적 중 어느 공급사에
발주할지 정하는 단계입니다. 이때 에이전트는 회사의 **전략과 KPI**를 판단 근거로 씁니다. 전략과 KPI는 전략 보드와
온톨로지에 정리되어 있습니다.

- **상충 없음:** 이 업무에 걸린 KPI 를 모두 만족하는 쪽을 고릅니다.
- **상충 + 우선순위 있음:** 서로 부딪치는 KPI 가 있으면, 미리 정해 둔 **판단 우선순위**대로 고릅니다.
- **상충 + 우선순위 없음:** 우선순위를 정하지 않았거나 같으면, 스스로 정하지 않고 **담당자에게 묻습니다.**

이 문서는 세 경우를 하나씩 직접 실행해 확인하는 테스트 진행 문서입니다. 마지막 통합 시나리오에서는 긴 프로세스 한 건 안에서
세 경우가 차례로 일어납니다. 시나리오마다 설명 영상이 있습니다.

| 유형 | 프로세스(단계 수) | 에이전트의 판단 | 영상 |
|---|---|---|---|
| 1 정상 | 소모품 정기 구매(7) | 지배 KPI 를 모두 만족하는 쪽 선택 | [sc1.mp4](video/ontology-agent-decision/sc1.mp4) |
| 2.1 상충 + 우선순위 | 생산 자재 긴급 구매(7) | 우선순위가 높은 KPI 를 따라 선택, 포기한 KPI 명시 | [sc21.mp4](video/ontology-agent-decision/sc21.mp4) |
| 2.2 상충 + 우선순위 미정 | 설비 부품 구매(7 + 검수 분기) | 업무 화면에 질문을 남기고 기다림 → 답을 근거로 이어서 처리 → 택한 기준으로 검수 Gateway 분기 | [sc22.mp4](video/ontology-agent-decision/sc22.mp4) |
| 통합 | 생산라인 증설 자재 조달(9 + 검수 분기) | 판단 3단계: 상충 없음 → 우선순위 → 질문, 설비 부품의 기준으로 검수 분기 | [scx.mp4](video/ontology-agent-decision/scx.mp4) |

## 시나리오 개요

가상 구매 조직이 구매 요청부터 입고 검수까지 처리합니다. 시나리오 1·2.1·2.2 의 프로세스는 같은 7단계입니다.

| # | 단계 | 담당 |
|---|---|---|
| 1 | 구매 요청 — 품목·수량·필요일·사유 | 요청 부서 |
| 2 | 요청 접수·사양 확인 | 구매 담당 |
| 3 | 견적 접수 — 후보 공급사 두 곳의 단가·납기·품질 합격률 | 구매 담당 |
| 4 | **공급사 선정 판단** — 온톨로지에서 판단 근거를 확인하고 공급사 한 곳을 고름. 판단 근거는 이 업무를 지배하는 전략·KPI, 우선순위, 상충 관계 | **구매 판단 에이전트**(사용자 태스크에 에이전트 배정) |
| 5 | 발주 승인 — 에이전트의 선정과 근거 검토 | 구매팀장 |
| 6 | 발주서 발행 | 구매 담당 |
| 7 | 입고·검수 | 요청 부서 |

통합 시나리오의 프로세스(9단계)는 4단계 자리에 에이전트 판단이 세 번 들어갑니다. 포장 부자재, 핵심 자재, 설비 부품 순서입니다.

설비 부품 구매와 통합 시나리오는 7단계(검수) 자리가 **검수 방식(적용 기준)** Gateway 로 갈립니다. 판단 단계에서 품질을 택했으면
**입고·검수**(요청 부서), 단가를 택했으면 **강화 검수**(품질 관리)입니다. 담당자의 답이 보고서에만 남지 않고 프로세스 흐름까지
바꾸는 예입니다.

프로세스(통합은 판단 단계)마다 연결된 KPI 가 다릅니다. 그래서 에이전트의 판단 방식도 달라집니다.

| 프로세스 · 판단 단계 | 근거 KPI | 상충 | 판단 우선순위 |
|---|---|---|---|
| 소모품 정기 구매 | 소모품 구매 단가 절감률 · 정기 구매 계획 준수율 | 없음 | — |
| 생산 자재 긴급 구매 | 긴급 자재 납기 준수율 ↔ 긴급 자재 구매 단가 절감률 | 있음 | 납기 1 · 단가 2 (시나리오에서 직접 설정) |
| 설비 부품 구매 | 설비 부품 품질 합격률 ↔ 설비 부품 구매 단가 절감률 | 있음 | 미정 |
| 증설 · 포장 부자재 공급사 선정 | 증설 포장재 단가 절감률 · 증설 포장재 납기 계획 준수율 | 없음 | — |
| 증설 · 핵심 자재 조달 판단 | 증설 핵심자재 납기 준수율 ↔ 증설 핵심자재 단가 절감률 | 있음 | 납기 1 · 단가 2 |
| 증설 · 설비 부품 공급사 선정 | 증설 설비부품 품질 합격률 ↔ 증설 설비부품 단가 절감률 | 있음 | 미정 |

## 사전 조건

- **화면:** 일반 BPM 화면(`http://localhost:8081`)
- **계정:** 관리자 계정(예: `manual-shots@uengine.org`) — 실행 버튼과 전략 보드 편집에 필요합니다.
  데모에서는 이 한 계정이 요청 부서·구매 담당·구매팀장 역할을 모두 맡습니다.
- **데모 데이터:** 아래 명령으로 만듭니다. 프로세스 4개, KPI 12개(상충 4쌍), '구매 판단 에이전트'가 생기고, 정의 지도의
  **구매 운영 › AI 판단 시나리오**에 배치됩니다. 다시 실행하면 지우고 새로 만듭니다.

  ```bash
  python3 scripts/demo/ontology-decision/seed.py           # 만들기
  python3 scripts/demo/ontology-decision/seed.py --cleanup # 지우기
  ```

- **에이전트 실행기:** 기본 에이전트 실행기(`langchain-react`, 포트 8011)가 떠 있어야 합니다. 판단 단계는 이 실행기가 맡습니다.
- **에이전트 설정:** 구매 판단 에이전트에는 도구 `strategy-ontology`(전략–실행 온톨로지, 읽기 전용)가 연결되어 있어야 합니다.
  에이전트는 이 도구의 **판단 근거 조회**로 먼저 근거를 확인합니다. 데모 데이터에는 이미 연결되어 있습니다.

### 판단 단계 설정 — 사용자 태스크 + 에이전트

판단 단계는 **사용자 태스크에 에이전트를 배정**해 만듭니다. 정의 편집기에서 그 단계를 더블클릭하고 **에이전트** 탭에서
다음과 같이 지정합니다. 데모 데이터에는 이미 지정되어 있습니다.

| 항목 | 값 |
|---|---|
| 에이전트 연구 방식 | 기본 에이전트 |
| 완료 수준 | 완성(에이전트가 작업을 자동으로 완료) |
| 미리 설정된 에이전트 사용 | ✓ |
| 에이전트 | 구매 판단 에이전트(도구는 에이전트 설정의 `strategy-ontology`를 씀) |

![에이전트 탭](images/ontology-agent-decision/1-01b-agent-tab.png)
- **입력 문구:** 각 단계에 적는 요청·접수·견적·승인·발주·검수 문구는 `scripts/demo/ontology-decision/scenarios.json` 에 있습니다.
  복사해서 그대로 쓰면 됩니다.

### 모든 시나리오에 공통인 단계 (요청 → 접수 → 견적)

1. 정의 지도에서 **구매 운영 › AI 판단 시나리오 › (프로세스)**를 엽니다. 레인은 넷입니다(요청 부서·구매 담당·구매 판단 에이전트·
   구매팀장). 구매 판단 에이전트 레인의 단계가 에이전트가 맡는 단계입니다.
2. 오른쪽 위 **실행** → **구매 요청**을 쓰고 **제출 완료**. 인스턴스 화면(칸반)으로 이동합니다.
3. 칸반의 '진행 중'에서 **요청 접수·사양 확인**을 열어 쓰고 **제출 완료**.
4. 이어서 **견적 접수**를 열어 두 공급사의 견적을 쓰고 **제출 완료**. 이제 에이전트 판단 단계가 시작됩니다.

### 모든 시나리오에 공통인 마무리 (승인 → 발주 → 검수)

에이전트 판단이 끝나면 **발주 승인**(구매팀장) → **발주서 발행**(구매 담당) → **입고·검수**(요청 부서)를 차례로 열어 쓰고
**제출 완료**합니다. 검수 Gateway 가 있는 프로세스는 입고·검수 대신 강화 검수가 열릴 수 있습니다. 마지막 단계를 제출하면 인스턴스가 '완료'가 됩니다.

## 시나리오 1 — 정상: 전략·KPI 에 맞춰 진행

**목적:** 상충이 없을 때, 에이전트가 이 업무를 지배하는 KPI 를 근거로 판단하는지 확인합니다.

1. **소모품 정기 구매**를 열고 실행합니다.

   ![프로세스 상세 — 7단계](images/ontology-agent-decision/1-01-process.png)
   ![구매 요청](images/ontology-agent-decision/1-02-request.png)

2. 요청 접수와 견적 접수를 제출합니다(A: 박스당 21,500원·7일, B: 23,900원·7일).

   ![요청 접수·사양 확인](images/ontology-agent-decision/1-03-receive.png)
   ![견적 접수](images/ontology-agent-decision/1-04-quote.png)

3. 10~20초 뒤 **공급사 선정 판단**이 '완료됨'으로 옮겨 가고, **발주 승인**이 '진행 중'으로 옵니다. 판단 단계를 열어 보고서를 봅니다.

   ![칸반 — 에이전트 완료](images/ontology-agent-decision/1-05-kanban.png)
   ![에이전트 보고서](images/ontology-agent-decision/1-06-report.png)

4. 발주 승인 → 발주서 발행 → 입고·검수로 마칩니다.

   ![발주 승인](images/ontology-agent-decision/1-07-approve.png)
   ![인스턴스 완료](images/ontology-agent-decision/1-08-done.png)

**확인 포인트**

- [ ] 보고서의 결론이 **A 공급사**다(단가가 낮고 납기는 같다).
- [ ] 보고서에 후보 비교표가 있고, 근거에 **소모품 구매 단가 절감률**·**정기 구매 계획 준수율**의 목표·현재값이 인용된다.
- [ ] 사용자에게 묻지 않고 바로 완료되며, 발주 승인이 '진행 중'으로 온다.

## 시나리오 2.1 — 상충 + 우선순위: 에이전트가 우선순위로 선택

**목적:** 두 KPI 가 상충할 때 전략 보드에서 정한 **판단 우선순위**를 에이전트가 따르는지 확인합니다.

1. **전략 보드**에서 전략 **협력사 납기 신뢰도 향상**을 고릅니다. 오른쪽 KPI 목록에서 **긴급 자재 납기 준수율**의
   연필(수정)을 누릅니다. **판단 우선순위**를 `1 (최우선)`으로 고릅니다. **상충하는 KPI** 칸에는
   `긴급 자재 구매 단가 절감률`이 이미 들어 있습니다(여기서 추가·삭제 가능). **저장**을 누릅니다.

   ![판단 우선순위 1](images/ontology-agent-decision/21-00-priority.png)

2. 같은 방법으로 전략 **구매 원가 절감**의 **긴급 자재 구매 단가 절감률**을 우선순위 `2`로 저장합니다.
   KPI 카드에 **우선 1**과 **상충 · …** 표시가 붙습니다.

   ![우선·상충 표시](images/ontology-agent-decision/21-00b-board.png)

3. **생산 자재 긴급 구매**를 실행하고 요청·접수·견적을 제출합니다(A: 38,000원·9일, B: 44,500원·3일, 필요일 5일 이내).

   ![프로세스 상세](images/ontology-agent-decision/21-01-process.png)
   ![구매 요청](images/ontology-agent-decision/21-02-request.png)
   ![요청 접수](images/ontology-agent-decision/21-03-receive.png)
   ![견적 접수](images/ontology-agent-decision/21-04-quote.png)

4. 공급사 선정 판단이 완료되면 보고서를 확인합니다.

   ![칸반](images/ontology-agent-decision/21-05-kanban.png)
   ![에이전트 보고서 — 우선순위로 선택](images/ontology-agent-decision/21-06-report.png)

5. 승인 → 발주 → 검수로 마칩니다.

   ![발주 승인](images/ontology-agent-decision/21-07-approve.png)
   ![인스턴스 완료](images/ontology-agent-decision/21-08-done.png)

**확인 포인트**

- [ ] 보고서의 결론이 **B 공급사**(납기 3일)다.
- [ ] 근거에 **택한 기준: 긴급 자재 납기 준수율(우선순위 1)**, **포기한 기준: 긴급 자재 구매 단가 절감률(우선순위 2)**이 있다.
- [ ] 사용자에게 묻지 않는다(공급사 선정 판단이 '답변 대기'로 가지 않는다).
- [ ] (반대로 확인) 두 KPI 의 우선순위를 뒤바꿔(단가 1 · 납기 2) 다시 실행하면 결론이 **A 공급사**로 바뀐다.

## 시나리오 2.2 — 상충 + 우선순위 미정: 에이전트가 담당자에게 질문

**목적:** 판단 우선순위가 없을 때 에이전트가 스스로 정하지 않는지 확인합니다. 업무 화면에서 담당자에게 묻고, 받은 답을
근거로 이어서 처리해야 합니다.

1. **전략 보드**에서 전략 **협력사 관리 체계 고도화**의 **설비 부품 품질 합격률**을 수정 화면으로 엽니다.
   **판단 우선순위**가 `미정 — 상충 시 담당자에게 묻기`이고, 상충 KPI 가 `설비 부품 구매 단가 절감률`인지 확인한 뒤 **취소**로 닫습니다.

   ![우선순위 미정](images/ontology-agent-decision/22-00-no-priority.png)

2. **설비 부품 구매**를 엽니다. 이 프로세스에는 발주서 발행 뒤에 **검수 방식(적용 기준)** Gateway 가 있습니다.
   - 품질 우선 → **입고·검수**(요청 부서)
   - 단가 우선 → **강화 검수**(품질 관리 — 전수 시운전·시험 성적서·보증 조건 확인)

   Gateway 는 공급사 선정 판단 폼의 **적용 기준** 칸을 읽습니다. 이 칸은 에이전트가 판단 근거 결과(택한 KPI)로 채웁니다.
   실행하고 요청·접수·견적을 제출합니다(A: 1,840,000원·품질 97.2%, B: 2,150,000원·품질 99.7%).

   ![프로세스 상세 — 검수 Gateway](images/ontology-agent-decision/22-01-process.png)
   ![구매 요청](images/ontology-agent-decision/22-02-request.png)
   ![요청 접수](images/ontology-agent-decision/22-03-receive.png)
   ![견적 접수](images/ontology-agent-decision/22-04-quote.png)

   `user_choice`, **적용 기준**은 `설비 부품 품질 합격률`입니다.

- [ ] 견적 접수 직후 공급사 선정 판단이 **완료되지 않고** '답변 대기'로 멈춘다.
- [ ] 질문 카드의 선택지가 **설비 부품 품질 합격률**·**설비 부품 구매 단가 절감률** 두 개다.
- [ ] 품질을 고르면 결론이 **B 공급사**(품질 99.7%)이고, 근거에 **사용자 선택**이 남는다.
- [ ] (반대로 확인) 단가를 고르면 결론이 **A 공급사**다.
- [ ] 품질을 고른 건은 **입고·검수**, 단가를 고른 건은 **강화 검수**로 간다. 다른 쪽 업무는 진행 중이 되지 않는다.
- [ ] '취소'로 답하면 에이전트는 판단을 보류한다는 보고서로 마치고, 다음 단계(구매팀장)에게 결정을 넘긴다.

## 통합 시나리오 — 긴 프로세스 한 건에서 세 경우가 차례로

**목적:** 한 프로세스에 판단 단계가 여럿일 때, 단계마다 다른 KPI 를 근거로 서로 다른 방식으로 판단하는지 확인합니다.

**판단 적용 활동:** KPI 수정 화면에서 **연관 프로세스**를 고르면 **판단 적용 활동**을 지정할 수 있습니다. 비워 두면 그 프로세스의
모든 판단 단계에 적용되고, 고르면 그 단계에만 적용됩니다. 수동 입력 KPI 도 프로세스에 연결할 수 있습니다. 이때는 측정에
쓰지 않고 판단 근거로만 씁니다.

1. 정의 지도에서 **생산라인 증설 자재 조달**을 엽니다. 요청 → 접수 → 견적 → 에이전트 판단 3단계 → 통합 승인 → 발주 → 검수, 9단계입니다.

   ![프로세스 상세 — 9단계](images/ontology-agent-decision/x-01-process.png)

2. 전략 보드에서 **증설 핵심자재 납기 준수율**(전략: 협력사 납기 신뢰도 향상)을 엽니다. 다음 설정을 확인하고 **취소**로 닫습니다.
   - 판단 적용 활동: **핵심 자재 조달 판단**
   - 우선순위: 1
   - 상충: 증설 핵심자재 단가 절감률

   ![KPI 판단 적용 활동](images/ontology-agent-decision/x-00-kpi-scope.png)

3. 실행 → 요청(3품목) → 접수 → 견적(품목마다 두 공급사)을 제출합니다.

   ![구매 요청](images/ontology-agent-decision/x-02-request.png)
   ![요청 접수](images/ontology-agent-decision/x-03-receive.png)
   ![견적 접수](images/ontology-agent-decision/x-04-quote.png)

4. 에이전트 판단 단계가 차례로 진행됩니다. 칸반이 실시간으로 바뀝니다.

   ![칸반 — 판단 진행](images/ontology-agent-decision/x-05-kanban.png)

5. **판단 1 · 포장 부자재 공급사 선정**의 보고서: 상충이 없어 두 KPI 를 함께 만족하는 **A**.
   **판단 2 · 핵심 자재 조달 판단**의 보고서: 납기(우선순위 1)를 따라 **B**, 단가는 포기.

   ![판단 1 보고](images/ontology-agent-decision/x-06-report-packaging.png)
   ![판단 2 보고](images/ontology-agent-decision/x-07-report-core.png)

6. **판단 3 · 설비 부품 공급사 선정**은 '답변 대기'로 멈춥니다. 업무를 열어 질문 카드에서 **품질**을 고르고 확인합니다.

   ![답변 대기](images/ontology-agent-decision/x-08-kanban-waiting.png)
   ![질문 카드](images/ontology-agent-decision/x-09-question.png)

7. 답을 받은 에이전트가 이어서 처리합니다. 사용자 선택(품질)을 근거로 **B**를 고릅니다.

   ![판단 3 보고](images/ontology-agent-decision/x-10-report-parts.png)

8. 인스턴스의 **산출물** 탭에서 세 판단의 보고를 한꺼번에 볼 수 있습니다. 통합 발주 승인 → 발주서 발행을 제출하면
   검수 Gateway 가 **설비 부품 판단**의 적용 기준을 읽습니다. 품질을 골랐으므로 입고·검수로 가고, 단가를 골랐다면 강화 검수로 갑니다.

   ![산출물 — 세 판단](images/ontology-agent-decision/x-11-outputs.png)
   ![통합 발주 승인](images/ontology-agent-decision/x-12-approve.png)
   ![검수 Gateway](images/ontology-agent-decision/x-12-branch.png)
   ![인스턴스 완료](images/ontology-agent-decision/x-13-done.png)

**확인 포인트**

- [ ] 판단 1 → **A**(상충 없음), 판단 2 → **B**(우선순위), 판단 3 → 질문 후 **B**(사용자 선택: 품질).
- [ ] 판단 1·2 는 묻지 않고 넘어가고, 판단 3 에서만 '답변 대기'가 된다.
- [ ] 각 보고서에는 그 단계의 KPI 만 근거로 나온다(다른 단계의 KPI 가 섞이지 않는다).

## 자주 묻는 질문

**Q. 판단 우선순위와 '전략적 중요도'는 무엇이 다른가요?**
전략적 중요도(★)는 달성률을 합산할 때 쓰는 가중치입니다. 판단 우선순위는 상충할 때 어느 쪽을 따를지 정하는 순번입니다.
1 이 가장 앞섭니다. 둘은 따로 정합니다.

**Q. 상충은 어디서 정하나요?**
전략 보드의 KPI(또는 전략) 수정 화면 **상충하는 KPI(전략)** 칸에서 정합니다. 한쪽에서 연결하면 양쪽 모두 상충으로 봅니다.
상충은 사람이 선언합니다. 에이전트가 추측해서 만들지 않습니다.

**Q. 한 프로세스에 에이전트 판단 단계가 여럿이면?**
KPI 의 **판단 적용 활동**으로 단계마다 근거 KPI 를 나눕니다(통합 시나리오). 비워 두면 그 프로세스의 모든 판단 단계에 적용됩니다.

**Q. 답변 대기 업무에 아무도 답하지 않으면?**
업무는 답을 받을 때까지 보류 상태로 남습니다. 실패로 처리되거나 재시도 횟수를 쓰지 않습니다. 답하면 다음 확인 주기(몇 초)
안에 이어서 처리됩니다.

**Q. 우선순위가 같으면?**
동률은 정하지 않은 것과 같게 보고 담당자에게 묻습니다.

**Q. 에이전트의 판단 결과로 Gateway 를 분기하려면?**
판단 단계에 전용 폼을 두고 `decision_mode`(판단 방식)·`decision_chosen`(적용 기준) 필드를 넣습니다. 에이전트 실행기가
판단 근거 결과로 두 칸을 채웁니다. 판단 방식은 `aligned`·`priority`·`user_choice`·`deferred`, 적용 기준은 택한 KPI 이름입니다.
Gateway 뒤 연결선의 조건식은 `<폼 id>: '품질' in decision_chosen`처럼 씁니다. 판단 단계가 기본 폼(defaultform)을 쓰면 뒤 단계의
결과에 덮여 Gateway 가 읽지 못하므로, 판단 단계마다 폼을 따로 둡니다.

**Q. 서비스 태스크로도 만들 수 있나요?**
에이전트 실행기가 없는 환경이면 판단 단계를 서비스 태스크로 둘 수 있습니다. 이때는 실행 엔진이 직접 실행합니다
(`seed.py --service-task`). 판단·질문·보고는 같게 동작합니다. 다만 정의 편집기에서 에이전트 탭으로 설정을 바꿀 수 없어,
원래 흐름인 사용자 태스크 + 에이전트를 권장합니다.

**Q. 에이전트가 판단 근거를 어디서 가져오나요?**
전략–실행 온톨로지의 **판단 근거 조회**에서 가져옵니다. 이 업무(프로세스·단계)에 연결된 KPI, 그 상위 전략, KPI 들 사이의 상충과
우선순위를 읽습니다. 결정 방식(상충 없음 / 우선순위 / 질문)은 이 조회 결과가 정합니다. 같은 설정이면 언제나 같은 방식으로
판단합니다.
