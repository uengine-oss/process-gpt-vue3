## Context

대화창 인계(`handover-driven-process-identification`)는 산출물을 받는 방마다 복사한다.

- 화면(`ProcessGPTBackend.createChatHandover`)이 고른 산출물을 읽어 받는 방 작업 폴더
  `files/skills/{tenant}/{받는 방}/` 에 올리고, 브리핑 메시지에 작업 폴더 항목으로 싣는다.
- 에이전트(deepagents `executor.py`)는 실행을 시작할 때 방 작업 폴더를 내려받고
  (`download_workspace_directory`, 실행 시작부), 끝나면 통째로 올린다(`upload_workspace_directory`).
  파드 로컬 디스크는 공유되지 않아 Storage 가 유일한 영속 작업 폴더다.
- 병렬 인계(2026-10-23)는 받는 사람 수만큼 `createChatHandover` 를 부른다. 사본은 받는 사람 수 ×
  산출물 수만큼, 단계마다 곱해져 늘어난다. 넘긴 사람은 받은 쪽 사본을 보지 못한다.

필요한 것은 git 이 아니라 git 워크트리의 작업 모델이다(proposal 참조).

## Goals / Non-Goals

**Goals:**
- 스레드마다 저장소 하나, 방마다 브랜치 하나. 인계는 복사가 아니라 분기.
- 같은 내용은 한 번만 저장. 커밋은 불변.
- 넘긴 사람을 포함해 스레드 참여자가 다른 브랜치의 파일·이력을 읽는다.
- 합류에서 갈래 브랜치를 병합하고, 충돌은 사람이 고른다.
- 동시에 끝나는 갈래들이 서로의 커밋을 잃지 않는다.

**Non-Goals:**
- git 프로그램·객체 형식·원격 저장소(push/pull). 외부 git 서버.
- 텍스트 줄 단위 자동 병합, 파일 내용 차이(diff) 화면.
- 이미 복사 방식으로 넘긴 방의 전환(그대로 둔다).
- 같은 방 안에서 여러 사람이 동시에 편집하는 충돌 해결(한 방 = 한 브랜치, 지금처럼 마지막 턴이 이긴다).

## Decisions

### 1. git 대신 DB + 내용 주소 Storage
- 내용: Storage `files` 버킷 `artifacts/{tenant}/objects/{sha256}` 에 한 번만 올린다(이미 있으면 건너뜀).
- 메타: DB 테이블 네 개.

| 테이블 | 열 | 뜻 |
|---|---|---|
| `artifact_repos` | id, tenant_id, origin_room_id(유일) | 스레드 저장소 |
| `artifact_commits` | id, repo_id, parents uuid[], room_id, author_id, reason(`handover`·`task_done`·`agent_turn`·`merge`), tree jsonb(경로 → {sha256, size, content_type}), created_at | 불변 스냅샷 |
| `artifact_branches` | repo_id, room_id(유일), head_commit_id, base_commit_id, created_at | 방 = 브랜치 |
| `handover_events` + `base_commit_id` | | 받는 방이 시작한 커밋 |

- tree 는 스냅샷 전체(경로 → 내용 해시)를 담는다. 인계 산출물은 수십 개 이하라 부모를 따라가며 합치는
  방식보다 단순하고, 어느 커밋이든 한 번에 연다.
- 대안: Storage 에 git bare 저장소 — Storage 에는 조건부 쓰기가 없어 동시에 끝나는 갈래가 ref 를 서로
  덮어쓴다. git 서버 — git 의미는 그대로지만 운영 구성이 늘고 이진 산출물이 대부분이라 이득이 적다.

### 2. 브랜치 갱신은 조건부(낙관적 잠금)
`commit_branch(room_id, expected_head, tree, reason)` DB 함수가 한 트랜잭션에서 커밋을 넣고
`head_commit_id = expected_head` 일 때만 브랜치를 옮긴다. 다르면 오류를 내고 호출 쪽이 최신 head 를
다시 읽어 재시도한다. tree 가 head 와 같으면 커밋을 만들지 않고 head 를 돌려준다(바뀐 것 없음).
- 대안: 마지막 쓰기 승리 — 같은 방 커밋이 겹치면 잃는다.

### 3. 분기·병렬 인계
`createChatHandover` 는 파일을 올리지 않는다.
1. 넘기는 방 작업 상태를 커밋(`handover`)한다. 넘기는 방에 브랜치가 없으면(스레드 시작 방) 저장소와 브랜치를 만든다.
2. 인계 창에서 고른 경로만 남긴 tree 로 받는 방 브랜치를 만든다(`base_commit_id` = 1의 커밋).
3. 병렬 인계는 1을 한 번만 하고 2를 받는 사람 수만큼 한다.

인계 창 산출물 후보는 넘기는 방 브랜치 head 의 tree 경로 목록이다. 첨부(`chat_attachments`)·지식 문서는
지금처럼 고를 수 있고, 고르면 내용을 객체로 올려 tree 에 넣는다.

### 4. 커밋 시점(사용자 결정 2026-10-23)
- 인계할 때: 화면(3.1).
- 받은 할 일을 완료할 때: 화면의 완료 처리(할 일 목록 완료, `completeReceivedHandoverTask`)에서 그 방 작업 상태를 커밋.
- 에이전트 턴이 끝날 때: deepagents 가 업로드 대신 커밋(5).

"그 방 작업 상태"는 브랜치 head tree 에, 그 방에서 head 이후 새로 생기거나 바뀐 작업 폴더 파일을 얹은 것이다.
사람이 화면에서 올린 파일은 지금처럼 방 작업 폴더에 먼저 놓이고, 커밋 시점에 tree 로 들어간다.

**사람이 미리보기로 고친 파일은 바로 커밋한다(사용자 결정 2026-10-26, reason `edit`).**
미리보기 편집은 화면 메모리만 바꾸고 어디에도 저장하지 않아서, 고친 내용이 새로 고치면 사라지고 에이전트·넘긴 사람에게
이어지지 않았다. 입력이 멈추고 1.2초 뒤 그 경로만 바꾼 tree 로 `commit_branch` 한다(방을 떠나면 바로).
화면 패널은 에이전트 실행 기록으로 다시 그려지므로, 방을 열 때 이 방 브랜치 head 내용으로 글 파일을 맞춘다.

### 5. 에이전트 작업 폴더
- 시작: 그 방에 브랜치가 있으면 head tree 의 객체를 내려받아 작업 폴더에 펼친다
  (`download_workspace_directory` 대신). 펼친 tree 를 기억한다(`expected_head`).
- 끝: 작업 폴더를 훑어 tree 를 만들고, 새 객체만 올린 뒤 `commit_branch(..., reason='agent_turn')`.
  head 가 그새 바뀌었으면(같은 방의 사람 커밋) 최신 head 위에 바뀐 경로만 다시 얹어 재시도한다.
- 브랜치가 없는 방(예전 방, 인계와 무관한 방)은 지금처럼 방 폴더를 내려받고 올린다.

### 6. 합류
같은 방에서 나눠 준 묶음(`group_id`) 뒤에 그 방에서 다음 인계가 일어나면(작업 흐름 그림의 합류 규칙과 같다),
갈래 브랜치들 head 와 넘기는 방 head 를 3-way 로 비교한다(기준 = 묶음을 나눈 커밋).
- 한 갈래만 바꾼 경로: 그 내용.
- 둘 이상이 다르게 바꾼 경로: 충돌. 인계 창이 경로별로 갈래를 고르게 하고, 고르기 전에는 넘기지 않는다.
- 병합 커밋(`merge`)의 parents 는 넘기는 방 head + 갈래 head 들이다. 받는 방 브랜치는 이 커밋에서 시작한다.

### 7. 다른 브랜치 읽기와 화면
- 읽기: 같은 테넌트 사용자는 저장소·커밋·브랜치를 읽는다(지금 `handover_events`·`chats` 와 같은 테넌트 정책).
  쓰기는 `commit_branch` 함수로만, 자기 방 브랜치에만.
- 화면: 새 진입 버튼은 만들지 않는다.
  - 작업 흐름 그림 카드: 그 단계 브랜치가 base 이후 추가·변경한 경로.
  - '산출물 파일' 탭: 이 방 브랜치 파일 + 스레드의 다른 브랜치 head 파일(브랜치별로 묶어 읽기 전용).

### 9. 변경 알림(사용자 결정 2026-10-26)
알릴 사람은 **넘긴 사람**뿐이다. 갈래끼리는 서로 영향이 없고, 아래쪽(이미 넘겨받은 방)은 받은 시점 스냅샷이 설계다.
- 화면 안 표시: 넘긴 사람 방이 스레드 저장소의 `artifact_branches` 변경을 구독한다(Realtime). 다른 방 브랜치가
  바뀌면 '갈래 산출물'을 다시 읽고, 그 탭을 보고 있지 않으면 탭에 점을 띄운다. 편집마다 알림을 보내면 소음이라 알림은 없다.
- 완료 알림: 인계받은 할 일(`handover_events.to_task_id`, `chat_handover`)이 `DONE` 이 되면 DB 트리거가 넘긴 사람에게
  `notifications` 행을 하나 넣는다. 사람은 화면에서, 에이전트는 deepagents 에서 할 일을 끝내므로 두 경로를 한 곳에서 덮는다.
  `DONE` 으로 바뀌는 순간에만 넣어 같은 할 일에 두 번 보내지 않는다.
- 대안: 화면에서 알림 보내기 — 에이전트가 끝낸 할 일을 놓친다. deepagents 에도 넣기 — 같은 규칙이 두 곳에 생긴다.

### 8. 기존 방
브랜치가 없는 방은 지금처럼 동작한다. 새 인계를 하는 순간(넘기는 쪽) 그 방 작업 폴더로 저장소·브랜치를 만든다.

## Risks / Trade-offs

- [같은 방에서 사람 편집과 에이전트 턴이 겹침] → `commit_branch` 조건부 갱신 + 재시도. 같은 경로를 둘 다 바꿨으면 나중 커밋이 이긴다(지금과 같은 수준, 이전 커밋에는 남는다).
- [docx 같은 이진 파일은 차이를 볼 수 없음] → 충돌은 "어느 쪽을 쓸지"만 고른다. 화면은 버전과 만든 사람·시각을 보인다.
- [tree 를 통째로 저장해 커밋이 커짐] → 경로·해시만 담아 산출물 수십 개 기준 수 KB. 내용 객체는 공유된다.
- [쓰이지 않는 객체가 남음] → 커밋은 불변이라 지우지 않는다. 정리는 이번 범위 밖(Open Questions).
- [테넌트 읽기 범위가 넓음] → 지금 대화 조회와 같은 범위다. 스레드 참여자로 좁히는 것은 별도 결정.

## Migration Plan

1. 마이그레이션: 테이블 네 개, `handover_events.base_commit_id`, `commit_branch` 함수, 정책. process-gpt-infra-docker
   `init.sql` 과 로컬 supabase 마이그레이션에 같은 내용.
2. deepagents: 브랜치가 있으면 펼치기·커밋, 없으면 기존 경로. 브랜치 없는 방이 많아도 동작이 같아 먼저 배포해도 안전하다.
3. 화면: 인계를 분기 방식으로 바꾸고, 완료 커밋·합류 선택·패널 표시.
4. 되돌리기: 화면을 복사 방식으로 되돌리면 새 인계는 다시 복사된다. 이미 브랜치로 넘긴 방은 deepagents 가
   브랜치를 계속 읽으므로 deepagents 는 그대로 둔다.
